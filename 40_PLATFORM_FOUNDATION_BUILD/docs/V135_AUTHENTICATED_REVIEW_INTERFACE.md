# V135 authenticated review interface

V135 groups an opt-in browser interface, fresh result detail selection, exact-pin decision submission, manual identical retries and browser security admission on the V133/V134 production composition. D-018, the pre-TO freeze and customer-data gate continue. V131 writeback execution stays paused pending partner approval-wait evidence. An approval records the existing durable decision and queues its existing intent; no external write is executed.

## Deployment and admission

Set `http.reviewUi = {allowedOrigin: 'https://review.example.test'}` on the durable service. Both production managed review reads and decisions must be configured. No additional pool, migration, dependency, provider or background task is introduced. All 59 previous migration bytes remain unchanged. Deploy the bundled `browser/` assets alongside `src/`; the exact four assets are loaded from fixed module-relative paths. No user-controlled filesystem path is resolved.

`GET /review` and its three fixed local CSS/ES-module resources require production readiness, IP/tenant admission, a verified SERVER_SESSION, `inbound:review`, and current request authorization with kind REVIEW_UI/phase ADMIT. Tenant and actor remain server-session owned. This interface consumes an existing deployment session; it adds no sign-in, identity provider, bearer-token input or synthetic production session. Configure the deployment's real SessionCookieAuthProvider with the same canonical HTTPS origin and secure HttpOnly host cookie. The deployment must provide current business permission, durable audit and provider health evidence. The existing managed read/decision posture and authorization remain authoritative for every API operation.

Enabling reviewUi applies an additional browser guard to review reads and decisions. Origin, when supplied, must equal the configured origin. Fetch Metadata, when supplied, must be same-origin (GET navigation with `none` is accepted). Every decision POST in this enabled configuration must supply that exact Origin and `x-review-ui: 1`; nonbrowser clients of this deployment must also meet that contract. No CORS headers or preflight grant are added. Missing, cross-origin, same-site and duplicate security headers deny before auth/business callbacks. The guard never infers trusted origin from Host or forwarded headers. When reviewUi is absent, existing API contracts are preserved and the UI routes are opaque 404.

All four assets use no-store, nosniff, no-referrer, same-origin resource/opener policies, denied camera/microphone/geolocation, and a CSP restricting scripts/styles/connections to self with no inline scripts, framing, objects, images, base changes or form navigation. Only GET to exact asset paths without queries/bodies is accepted. Unknown paths receive opaque responses. No embedded tenant/result data is present in the shell.

## Review and decision behavior

The interface browses the existing bounded metadata list with PENDING/DECIDED/ALL filters. Each next page uses the opaque cursor, including empty authorized scans that have continuation. Refresh restarts the live scan; no chronological or frozen-export promise is made. Selecting an item fetches its current detail before displaying exact event, adopted job/hash, result code, artifact hash and existing decision metadata. Server values are rendered with textContent and DOM nodes. Malformed or duplicate records, inconsistent status/decision fields and cross-object detail responses release no browser selection.

There is no document viewer, legal assessment or matter search. The operator reviews the source through their approved system, then explicitly confirms that review and supplies a canonical matter UUID for approval. This checkbox is a human UI acknowledgement, not independent source-review evidence or a replacement for server authorization. Reject supplies null matter. The UI never submits tenant/actor, raw document, provider evidence or unpinned result values. The selected exact job/hash is submitted to the existing decision endpoint. Concurrent changes remain subject to its durable conflict/authorization checks. A writeback job ID denotes an intent, not completed writeback.

The browser generates one cryptographically random decision key and retains an immutable request only in memory. Duplicate clicks cannot overlap. If a response/receipt is missing, times out, is malformed or fails acknowledgement verification, the interface clears displayed metadata and allows only a manual identical retry. It performs no automatic decision write. The same six-field body and key are replayed; verified receipts must match event, decision, matter and exact result pins. Explicit input rejection/conflict permits refreshing; session/access failures retain the request for safe replay after access is restored. A client deadline never proves server cancellation or rollback.

The tab uses same-origin credentials, no-store requests and redirect rejection; no browser storage or token persistence is used. Closing/reloading discards the retry key. The visible warning instructs operators to keep an unresolved tab open and check the durable decision before another action after losing it. Page hiding erases in-memory/DOM metadata, late responses cannot repopulate it, and a back-forward-cache restore reloads through authentication. Already displayed metadata cannot be retracted remotely after permission revocation.
