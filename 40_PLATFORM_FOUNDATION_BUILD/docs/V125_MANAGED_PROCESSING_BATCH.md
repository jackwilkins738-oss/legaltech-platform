# V125 — Managed artifacts, domain adoption and functional readiness

This authorised D-018 integration batch connects approved immutable artifact versions, durable worker results and domain state. Migration 054 and the six-pool managed composition extend V124. Existing HTTP/SQLite routes and customer-data deployment are not switched. Cloud SDKs, manifest persistence, scanner/release evidence and policy/business processors remain explicit deployment dependencies.

## Managed artifact contract

`ManagedWorkerArtifacts` requires bound `manifest.resolveVersion/probe`, `storage.readVersion/probe`, strict current `authorizeVersion` and strict `verifyEvidence` implementations. A manifest has exactly `{tenantId,id,kind,hash,objectKey,versionId,size,state,evidenceHash,region,revision}`. Keys must start with the exact tenant UUID, contain no empty/traversal segments and cannot be URLs. Every read selects an explicit immutable provider version; no latest-version alias or caller-supplied download URL is followed by this module. Policy manifests require PUBLISHED; payloads require PROCESSING_ALLOWED.

A storage SDK adapter returns exactly `{tenantId,objectKey,versionId,hash,contentLength,body}`. `body` is an async byte iterator with awaitable cleanup. Metadata must match the manifest. Streaming enforces the declared size, actual size, configured payload/policy limits, a 4,096-chunk ceiling and the actual SHA-256. The manifest is resolved again after streaming; revision, region, approval, evidence and immutable binding must be unchanged. Current authorization and independently verified evidence are rechecked before returning bytes. Iterator cleanup is awaited on success or failure; temporary owned chunk copies are wiped. Returned provider bytes are caller-owned; V124 runtime wipes its separate processing copies. Engine/provider copies are not guaranteed erased.

Deployment adapters must use the actual cloud SDK and approved version manifest, enforce transport/backpressure and cancellation, and bind region/residency, quarantine/scanner/parser approval, policy publication and revocation to the exact version/evidence hash. A caller-supplied state label is insufficient evidence. The adapter cannot prevent an SDK from allocating bytes before yielding them, nor make an uncooperative SDK cancel. No accepting synthetic provider is installed by the production factory.

## Transactional domain result adoption

`PostgresResultAdopter.adopt({tenantId,serviceActorId,jobId,signal})` uses the existing domain/outbox transaction and an independent queue-reader principal. It checks the result-writer grant/trigger posture, serializes each tenant/job with an advisory transaction lock, loads the immutable command and current active service/original-author/tenant identities, validates the bound inbound event or visible OPEN policy matter, and requires current adoption authority before reading and before committing a result. Authorization implementations must enforce current capability/object access for **both** identities plus lifecycle, containment and required handling gates. An active actor row alone is insufficient.

A missing worker receipt returns PENDING without domain mutation. Existing immutable receipts are compared against the exact tenant, job, kind, object, command hash and pinned artifact hash. Result code/hash, attempt and worker identity are copied into metadata-only `public.domain_job_results`. For inbound work, receipt insertion and RECEIVED → PROCESSED occur together. PROCESSED here means the verified callback result was adopted; it does not mean a legal decision was approved or a Proclaim/notification operation succeeded. Policy adoption records the pinned evaluation evidence without changing the matter or automatically implementing a decision. Application-specific output storage, human review and workflow effects remain separate.

Migration 054 creates the NOLOGIN `legaltech_domain_result_writer` group, forced tenant RLS, append-only result grants, and only the inbound status UPDATE column. A composite foreign key requires the public adoption row to exactly match an immutable private queue result, including all hashes, result code and claim fence/worker. The domain role receives no private-table SELECT/REFERENCES/ownership grants. PostgreSQL's internal referential integrity check enforces this linkage without granting application access to the private table. A deferred adoption trigger verifies the command/artifact binding, active identities and corresponding domain state at commit. A status-transition trigger requires the bound adoption row for result-writer updates. Protected mutation cannot commit a receipt-only or status-only inbound result.

Apply migration 054 and grant `legaltech_domain_result_writer` to the existing direct-login domain principal before enabling this path. The domain principal also requires the existing actors/tenants/command/inbound/matter access and outbox-writer membership. Private, worker-domain-reader and identity roles must not inherit the result-writer group; their posture probes now reject it. Earlier migration checksums are unchanged.

Identical adoption replays without changing the original adopter/time; conflicting results, missing receipts, disabled actors, closed/invisible matters and disabled/widened posture deny. A lost commit response reports DOMAIN_RESULT_COMMIT_OUTCOME_UNKNOWN. Reconcile by replaying the same adoption under current authority; never rerun processing merely because adoption acknowledgement was lost. Deferred constraint failures can also produce this conservative unknown response; no optimistic success is returned. Database transaction deadlines discard failed connections and block late transaction access.

## Managed deployment composition and canary

`createPostgresManagedProcessing` binds six distinct pools/principals: domain, outbox relay, queue producer, queue worker, read-only worker domain and queue result reader. It installs the actual managed artifact loader and durable result reader/adopter. Worker options cannot override artifact callbacks; canary options cannot replace the factory's actual pipeline/adopter. Construction connects or starts nothing. Caller-owned pools remain open while supervisors are undrained.

`managed.canary.run()` explicitly submits a newly generated command/job/event to a **pre-provisioned isolated synthetic tenant**. Deployment supplies the approved synthetic fixture manifest and expected deterministic processor output; fixture creation must attest `confirmedSynthetic:true`. This marker is a contract, not proof that arbitrary tenant data is synthetic. Do not configure a customer tenant or real documents as a health fixture. The canary follows the actual handler → supervised relay → queue claim → managed artifact → processor → queue receipt → domain adoption route. It does not start workers or fabricate completion. Both supervisors must already be running with authorized scopes that include the synthetic tenant.

The canary rejects replayed submission and any mismatched tenant/job/command/object/version/result. Current canary authority is required at run, submit, completion and probe. Fresh UUIDs prevent reuse of an old receipt as new evidence. A failed run invalidates previous success. Monotonic freshness defaults to 30 seconds, is bounded to 60 seconds maximum and denies rollback/nonfinite time. A deadline aborts the run; a stalled callback keeps that canary admitted until it actually settles. A submitted job may still finish after canary timeout and must be reconciled normally; there is no automatic cancellation/deletion or rollback of already committed processing.

Call `managed.start()` only after deployment startup admission, then explicitly run the canary before opening customer ingress. Arrange authorized periodic runs before evidence expires; no automatic health-job scheduler is introduced. During shutdown, stop new canary scheduling and await `managed.stop()` before closing pools. It aborts the relay, worker and active canary together and reports drained only after all three actually settle. A timed-out canary keeps the managed root undrained and prevents restart until settlement. Explicit restart invalidates prior canary health and requires a new successful run.

`managed.createReadiness({probes,...})` retains all 13 required production gates and binds OBJECT_STORAGE to the actual managed providers, QUEUE to the actual running pipeline plus fresh canary evidence, and WORKER_AUTHORIZATION to current authority plus fresh canary evidence. Failed/timed-out wrapper probes retain their admission until actual settlement; another evaluation receives unready instead of overlapping the same pending wrapper. `managed.probe()` also requires actual provider/pipeline posture and current fresh canary evidence. Bind the returned registered readiness facade to production HTTP admission; using unrelated accepting callbacks does not perform that integration.

## Validation and limits

See `TEST_RESULTS_V125.md`. Enabled PostgreSQL CI adds eight V125 cases for actual receipt/state linkage, exact private FK proof, forged/partial rollback, grants/RLS, permission withdrawal, disabled protection and the connected managed canary/readiness path. These use sealed synthetic SDK/evidence fixtures in a disposable database. All CI, including `postgres-security-integration`, must pass before merge. Actual PostgreSQL execution is skipped locally; real SDKs, permissions, scanner/release evidence, processors, managed shared drain, scheduling, deployed HTTP admission and customer data remain unvalidated.

Reference for the FK/RLS boundary: https://www.postgresql.org/docs/17/ddl-rowsecurity.html. Constraint validation can expose existence through errors; application errors remain sanitized, tenant RLS applies to the adoption row and metadata is never returned from a failed constraint.
