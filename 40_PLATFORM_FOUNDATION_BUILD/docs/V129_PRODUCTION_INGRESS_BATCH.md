# V129 — Production ingress integration batch

This batch connects approved managed upload references, validated Graph dispatch and published policy requests to the existing PostgreSQL domain/outbox/worker path. It also adopts that bridge at the legacy production inbound endpoint and binds source health to the nine-pool service. It does not create a cloud uploader, public Graph webhook receiver, legal approval or external Proclaim write.

## Stable source commands

`ManagedProcessingIngress` binds an actual `PostgresDomainJobHandlers` instance, registered production readiness and the same managed deployment drain. The deployment supplies a permanently pinned UUID namespace and current authoritative source resolvers. Uploads accept only tenant, authenticated actor and approved upload ID. Policy requests accept tenant, actor, matter and stable request ID. Graph dispatch accepts only subscription ID and validated notification fingerprint; the current server registry supplies tenant, service actor and approved artifact. Caller tenant/resource/actor claims cannot determine a Graph command.

Domain-separated SHA-256 derivation produces stable custom UUIDs for command, job and event identifiers. Purpose, tenant, source type, source identity and namespace are bound. Graph identities also bind the subscription. Reconstruction and lost replies retry the same identifiers and trace; changed actors, artifacts, source bindings or policy versions conflict against immutable PostgreSQL commands. Keep the namespace stable across instances and deployments. A namespace change requires reviewed migration/reconciliation; it is not a retry strategy. The existing source identity uniqueness additionally protects upload/Graph registration from duplicate replacement events.

No raw source identifiers, subjects, email bodies, document bytes or provider URLs enter commands. External origin keys are hashed before passing into the existing hashed domain registration field. Audit callbacks receive only tenant/actor/command/job/object/artifact IDs, artifact hash, source kind and phase. ACCEPTED proves domain/outbox commit, not processing, adoption, legal approval or provider writes.

## Current source proof and ownership

The deployment must implement `resolveUpload`, `resolveGraph`, `resolvePolicy`, `authorizeIngress`, `verifySourceEvidence`, `audit` and `probeSources`. The resolvers are authoritative current reads, not parsers for caller metadata. Bind real tenant/actor access, quarantine/processing clearance, immutable provider versions, evidence hashes and current revisions. Graph resolution must verify a previously validated notification against the current subscription registry, directory tenant, permitted resource and service identity. Never fetch a caller-provided resource URL. Policy resolution must verify exact matter access and current publication. Evidence verification must check actual scanner/parser/version attestations, not merely the presence of a hash.

The exact upload record contains `tenantId`, `actorId`, `sourceKey`, `payloadId`, `payloadHash`, `versionId`, `evidenceHash`, `revision`, `state`. Its source key equals the approved upload UUID and state is PROCESSING_ALLOWED. Graph adds the exact `subscriptionId` and a created/updated `changeType`; its source key equals the validated notification fingerprint. The policy record instead contains `matterId`, `policyVersionId`, `policyVersionHash`, with the same identity/version/evidence/revision fields; its source key equals the request UUID and state is PUBLISHED. Extra/accessor fields are rejected.

A source operation acquires global ingress admission before resolving a provider. It checks current authorization before resolution, verifies evidence, records an attempted audit, re-resolves the exact binding, re-verifies evidence and checks current authorization/readiness before command dispatch. Successful receipts must exactly match the expected durable command. Accepted audit failure or uncertain commit/release never produces a success receipt.

Defaults are 16 simultaneous operations and a 10-second cancellation deadline, configurable within 1–100 and 100–60,000ms. Cancellation retains the actual provider/command promise and global lease until settlement. Saturation rejects further ingress. Cancelled unresolved operations, uncertain release and stalled source probes close readiness. No local slot or remote lease expires to claim shutdown success; deliberate reconstruction requires exact reconciliation and settled-effect evidence.

## Service, HTTP and Graph adoption

Pass `ingress` options to `createDurablePostgresProcessingService` or `createPostgresProcessingService`. The factory supplies protected handlers/drain/readiness bindings, exposes `root.ingress` and `root.graphDispatch`, and adds source verification to mandatory object-storage readiness. Caller options cannot replace these protected dependencies or reopen direct commands.

With source ingress configured, the dedicated service's old direct inbound/policy command routes are disabled. Bind `createApiServer` to `root.readiness` and `processingIngress: root.ingress` for the production legacy inbound route. Its request is exactly `{uploadId}` with matching `Idempotency-Key`; session authentication supplies tenant/actor. Raw body/base64/attachment input and caller-selected payload hashes or tenant fields are rejected. Without the registered bridge, production cannot fall back to `platform.ingest`. Disconnects request cancellation. The synthetic app retains its existing demonstration contract; browser upload publishing and durable read/review screens still need explicit adoption.

`root.graphDispatch` or `createGraphProcessingDispatch(root.ingress)` accepts already validated created/updated notifications. It strips notification tenant/resource/trace claims and always reaches durable replay, including when a reference validator says duplicate. Source/commit uncertainty remains GRAPH_WEBHOOK_DISPATCH_FAILED so the validation queue can retry stable commands. Lifecycle/deleted notifications require separate subscription/delta handling; this adapter rejects them. Do not suppress this path with an in-memory completion set. The existing ephemeral webhook validation queue remains reference-only; a deployed durable intake and current Graph credentials are still required. The legacy client-state simulation endpoint is blocked in production.

Policy submission is server-side via `root.ingress.submitPolicy`; its result is a queued evaluation request, never a legal decision. The existing review/approval and output-write boundaries remain separate.

## Validation and deployment limits

Eighty-seven new boundary regressions cover configuration, source scopes, immutable bindings, reconstruction, strict authorization/evidence, audit ordering, cancellation, real ownership, safe errors, legacy HTTP adoption, direct-command bypass prevention and Graph duplicate retries. Ten enabled PostgreSQL cases cover actual registration/outbox replay, changed artifact conflicts, actor withdrawal, Graph service identity/tenant isolation, matter/policy bindings, production legacy HTTP, stalled-source drain retention, lost Graph acknowledgements and the source-bound nine-pool lifecycle.

All 55 migrations remain unchanged; no provider dependency is added. PostgreSQL is skipped locally and must pass in CI. Identity, source registries, permissions, evidence and Graph queue adapters in these cases are explicitly synthetic. Real cloud storage publishing, durable webhook intake, source authorization, audit delivery, Proclaim output and deployed permission evidence remain outstanding. This continues the authorized D-018 integration exception; the pre-TO freeze and customer-data deployment gate remain in force.
