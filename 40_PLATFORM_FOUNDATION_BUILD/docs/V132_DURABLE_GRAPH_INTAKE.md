# V132 durable Graph intake

This batch replaces the optional production webhook path's ephemeral intake with validated, immutable PostgreSQL notification metadata and fenced dispatch receipts. It continues the authorized D-018 integration exception. The pre-TO freeze and customer-data deployment gate remain in force. The reference V89/V91 in-memory classes remain reference fixtures; they are not used as the production durable queue.

## Durable admission and identities

`POST /api/v1/integrations/graph/webhooks` on a source-bound processing service requires the registered `root.graphIntake`. Without that component the route is unavailable. Microsoft Graph does not use a user session for this path: the existing isolated IP limiter, current authoritative subscription lookup, timing-safe clientState comparison, directory-tenant matching and, for rich notifications, verified validation-token claims guard admission. The validation-token challenge is a bounded plain-text echo, creates no work and cannot change subscription state. Ambiguous queries, unsupported encoding, malformed UTF-8/JSON and oversized bodies are rejected. Raw request bodies, secrets, JWTs, resource paths and confidential content never enter the inbox or public error responses.

Validation completes before source publication. The trusted `registerSource` provider then durably publishes an immutable approved mapping for V129 `resolveGraph`. Its input is the validated notification plus an abort signal: directory credentials, JWTs and raw resourceData have already been removed. The validated resource string is a locator to verify against the subscription's registered scope; it is never an arbitrary URL to follow. The provider must independently prove current object, tenant and permission evidence. It must not download/process documents or perform external business writes inside webhook registration.

The exact source acknowledgement is `{tenantId, subscriptionId, validatedFingerprint, notificationFingerprint, sourceEvidenceHash, sourceVersionHash}`. `validatedFingerprint` equals the reference validator's fingerprint. For created/updated document sources, compute `sourceVersionHash` with `graphApprovedSourceVersionHash(binding)` from the actual approved V129 Graph binding. Its tuple binds tenant, actor, subscription, change type, payload ID/hash, immutable version, evidence hash and revision; it excludes the source key to avoid a circular identity. `sourceEvidenceHash` equals that binding's evidenceHash. Compute the final `notificationFingerprint` with `graphSourceDeliveryFingerprint({tenantId, subscriptionId, validatedFingerprint, sourceVersionHash, eventType})`; durably register the source under that final fingerprint before returning. Registration must be immutable and idempotent, and current resolveGraph must return that exact approved binding.

A raw/basic Graph notice is not treated as a unique immutable source version. Identical notices without an event ID can admit a new approved version; exact same-version retries replay. This is approved-state convergence, not a complete audit of every transient source change. Microsoft's documented basic payload contains subscription/resource/change metadata, with resource data depending on the subscription: see [webhook delivery](https://learn.microsoft.com/en-us/graph/change-notifications-delivery-webhooks) and [changeNotification](https://learn.microsoft.com/en-us/graph/api/resources/changenotification?view=graph-rest-1.0). Current version discovery/delta recovery remains the source provider's responsibility.

All rows are validated before publication. Repeated identical rows within one payload publish once. Enqueue is atomic for each authoritative tenant. Cross-tenant batches commit separately and return 202 only after every tenant commit is verified; partial or lost acknowledgements return an unavailable/uncertain response and exact version retries remain safe. The response is `{status:"ACCEPTED", accepted, replayed}`. It proves durable validated source admission only. It does not prove execution, adoption, legal approval or a Proclaim write.

## PostgreSQL isolation and fencing

Migration `057_durable_graph_inbox.sql` adds `graph_security.notifications` and append-only `graph_security.receipts`, plus separate NOLOGIN producer/worker/reader groups. Provision three direct-login restricted principals and three separate pools. Producer grants permit only exact initial binding columns. Worker grants permit only claim/settlement columns and exact receipt columns. Reader grants are read-only. Both tables force tenant-context RLS. Every operation checks exact grants, isolated memberships, forced RLS, policy definitions, reviewed trigger-body hashes, trigger function ownership/schema/signatures, enabled trigger event types without conditions or column subsets, and deferred completion constraints. Existing session, shared security, domain and drain boundaries reject Graph-role mixing or direct Graph-table grants.

Every claim has an increasing attempt, server-generated 256-bit credential stored only as a hash, and an immutable worker identity. Only the exact current claim may settle. DONE requires an exact append-only receipt in the same transaction; a receipt without DONE cannot commit. Receipt completion is idempotent only with the identical claim and outcome hash. Tenant-scoped admission serializes active capacity; existing immutable retries work when capacity is full. Attempts and active capacity are explicit deployment settings, not business productivity thresholds.

There is deliberately no claim TTL, expiry recovery or forced release API. An old owner may still be executing an uncooperative callback. Elapsed time never authorizes a second worker. Known domain-command failures can requeue only after the actual callback settles, because V129 command/outbox replay is durable. Cancellation retains the claim, local slot and shared drain ownership until the actual callback and exact failure settlement finish. Lease acquisition waits for its actual acknowledgement before checking local cancellation and releasing the lease; shutdown also waits for any active health probe. Missing claim/receipt acknowledgements latch uncertainty. They do not trigger hot retry or optimistic readiness.

Created/updated dispatch uses the registered `dispatchGraphBound` route, which checks inbox tenant, source evidence and immutable source version against both source resolutions before any domain command. A stale, cross-tenant or changed source cannot commit a command. Current subscription and dispatch authorization are rechecked before execution; the database adapters also recheck current authorization after lock waits and before commit.

Deleted, missed, removed, reauthorization and unknown events use a separate trusted `dispatchControl` callback. Its input is tenant/subscription/final fingerprint/source evidence/source version/event type plus signal, never raw resource or document content. The exact acknowledgement is `{tenantId, subscriptionId, notificationFingerprint, sourceEvidenceHash, sourceVersionHash, status:"ACCEPTED"}`. Deployments must durably bind control intents and enforce current subscription scope; callback acceptance does not prove an external effect. Any uncertainty after control dispatch starts leaves the claim RUNNING for reconciliation and blocks optimistic health/restart. These notifications never create inbound document commands. The existing validator requires an ACTIVE unexpired registered subscription; recovery for expired/revoked subscriptions and real delta/lifecycle operations remain separate deployment work.

## Service composition and shutdown

Pass optional `webhooks` to `createDurablePostgresProcessingService` alongside the V129 `ingress` configuration:

- `producerOptions`: `{pool, expectedRole, actorId, authorizeEnqueue, maxAttempts?, maxQueued?, timeoutMs?}`.
- `workerOptions`: `{pool, expectedRole, actorId, workerId, authorizeWorker, timeoutMs?}`.
- `readerOptions`: `{pool, expectedRole, actorId, authorizeRead, timeoutMs?}`.
- `resolveSubscription`, optional `verifyValidationTokens`, `registerSource`, `authorizeDispatch`, `dispatchControl`, `probeGraph`.
- Current bounded `getScopes` and `authorizeScope`, and optional supervisor timing/batch settings.
- Optional intake `timeoutMs`, `maxPending`, `maxBodyBytes`; HTTP `maxGraphBodyBytes` is separately bounded.

The durable root requires twelve distinct processing/drain/Graph pools and direct-login roles. Caller options cannot replace bound inbox adapters, processing ingress, readiness, drain, relay operation or public HTTP intake. Constructors have no connection/timer side effects. The root exposes registered `graphIntake` and the trusted server-side `graphReader`; it exposes no public worker, receipt mutation or drain administration endpoint.

The supervised dispatcher shares the actual deployment drain and joins start/stop. Mandatory QUEUE readiness includes all three PostgreSQL inbox adapters, the actual Graph/source/control provider probe and a running supervisor. The dispatcher waits without claiming while processing canaries/readiness bootstrap or providers are unavailable. Raw intake uses current readiness too. Probes retain real non-overlap ownership through cancellation. Shutdown cannot report drained while callbacks, uncertain acknowledgements or source probes remain owned. Failed/uncertain instances must be reconstructed only after reviewed reconciliation.

For a crashed RUNNING owner, inspect metadata with the reader, verify actual provider/command outcomes and owner cessation, then use a reviewed operator recovery procedure. No runtime method is supplied to discard a held claim, drain lease, lost acknowledgement or uncertain control outcome. A non-expiring claim is containment evidence, not an assertion that an effect succeeded. Plan provider-specific reconciliation, retention and operating evidence before customer deployment.

## Verification and limits

Local tests cover 106 new constructor, payload, scope, version, replay, callback ownership, cancellation, receipt and HTTP boundaries. Seventeen enabled PostgreSQL CI cases cover the actual schema, grants/RLS, concurrent admission/capacity, reconstruction, atomic rollback, claim/receipt fencing, retry budgets, lock-time authorization withdrawal, catalog tampering, source-version replay, command/outbox integration, lost ingress acknowledgements, stalled drain ownership and the complete twelve-pool HTTP/worker/readiness/shutdown path.

Database validation uses the disposable PostgreSQL 17 CI instance. Source registries, Graph credentials/token claims, managed cloud storage, permission/evidence providers, control callbacks and document processors are synthetic fixtures. No real Microsoft tenant, live webhook registration, cloud publisher, Proclaim output or customer-data deployment is attested. Real endpoint hosting, credentials, current source/delta/lifecycle adapters, durable control reconciliation, permission evidence, retention and pilot release evidence remain outstanding. This batch changes no dependency or external subprocessor.
