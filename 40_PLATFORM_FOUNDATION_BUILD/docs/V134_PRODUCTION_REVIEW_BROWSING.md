# V134 production review browsing

This batch connects authorized durable result browsing to the V133 decision endpoint. It continues the authorized D-018 integration exception and preserves the pre-TO freeze and customer-data gate. V131 writeback execution remains paused pending partner evidence. A reviewed approval still queues the existing immutable intent; no executor or Proclaim output is introduced.

## Read contract

`GET /api/v1/processing/reviews` requires a verified OIDC/server session with `inbound:review`, current request authorization and IP/tenant admission. Tenant and actor come exclusively from that session. Supported query parameters are `status` (PENDING, DECIDED or ALL; default PENDING), `limit` (1–100; default 25), and `cursor`. Duplicate/unknown parameters, noncanonical limits, request bodies and invalid cursors are rejected. The optional route is absent without a registered managed read component.

The list returns `{items, nextCursor}`. Each item contains exactly `{eventId, status, resultJobId, resultHash, resultCode, artifactHash, decision, matterId, writebackJobId}`. Only adopted PROCESS_INBOUND results for inbound documents in PROCESSED, APPROVED or REJECTED state are eligible. An undecided event has null decision/matter/writeback fields; a decided item must match the immutable decision's exact job/hash and status. No raw result text, document bytes, resource path, provider token, event source metadata, tenant ID or actor details are returned. These metadata hashes do not supply the document itself or prove legal approval or external execution.

`GET /api/v1/processing/reviews/:eventId` returns one item under the same controls. Missing and unauthorized objects both return opaque 404. Supply its resultJobId/resultHash as expectedResultJobId/expectedResultHash to V133's decision POST. Concurrently decided events remain subject to the immutable decision/conflict checks. This is the API for a future review interface; no browser UI or authenticated document viewer is delivered here.

Current `authorizeRead` runs at ADMIT (event ID or null for list), ITEM for each candidate, and RELEASE for each visible item. ADMIT must prove current human/list scope; ITEM must independently prove current object/result/matter access. Denied candidates are omitted from lists; detail denial is opaque. Provider exceptions fail the whole operation. Actor type/status and tenant status are checked in the database before access and after provider/audit waits, including after RELEASE callbacks. All visible rows are withheld if final authority fails.

## Pagination and containment

Pages scan at most the requested limit in ascending event UUID order. The next cursor names the last scanned row, including denied candidates, so a page can be empty while having a continuation. No denied identifier or denied count is returned. A continuation indicates that another bounded scan may be useful; it does not assert additional authorized results. UUID order is deterministic, not chronological. The cursor's final page can be an empty scan.

Cursors use AES-256-GCM with a dedicated deployment-provided 32-byte key and version-specific authenticated context. They bind tenant, actor, status filter, last scanned UUID and expiry; canonical encoding, corruption, cross-context replay, wrong keys and expiry are rejected before connecting. Limit can change between pages. Deployments must share the same protected cursor key across replicas; reconstruction with that key preserves valid cursors. Default expiry is 15 minutes, configurable from one minute to one hour. Key rotation invalidates existing cursors safely. No cursor plaintext enters logs or audit callbacks.

Pagination is a live read, not a frozen export. Changes in status between pages or inserts before the cursor can require refreshing from the first page; a page never changes the result pin required for a decision. The read-only transaction uses READ COMMITTED so post-callback identity checks observe committed revocation. An acknowledged read reflects authorization at its final checks; permission changes after response delivery cannot retract already delivered metadata.

## PostgreSQL and service boundary

Migration 059 adds an isolated NOLOGIN `legaltech_review_reader` group with exact metadata-column SELECT grants and two tenant RLS read policies. The reader has no outbox, queue, decision-writing, result-writing, review scope-lock helper or general business write permission. It receives only tenant id/status and actor id/tenant/type/status needed for current identity verification. Queries explicitly bind the transaction tenant and actor. The public tenants table's id/status columns are not a tenant RLS data table; the application never returns those rows.

The store uses a dedicated direct-login principal and BEGIN READ ONLY. Health verifies the actual runtime catalog, exact effective column SELECT grants, absence of other role memberships or business writes, and all applicable PUBLIC/reader policies on actors, inbound events, results and decisions. Wider raw-result access, extra permissive policies, mixed reviewer/writer membership and leaked privileged APIs fail readiness. Other session, shared-security and drain boundaries reject reader-role mixing. The V133 reviewer verifier now explicitly recognizes the separate reader's read-only decision policy; its writer policy and narrow grants remain unchanged. Earlier migration bytes are unchanged.

Pass optional `reviewRead` to the production service factory: `{pool, expectedRole, cursorKey, authorizeRead, audit, probeRead, transactionTimeoutMs?, timeoutMs?, maxPending?, cursorTtlMs?}`. The deployment's mandatory authorizeRead, durable audit and read-provider health callbacks stay server-owned. Optional transactionTimeoutMs defaults to 5000; managed timeoutMs defaults to 10000 (100–60000), maxPending to 16 (1–100). Pool and role must differ from every processing/drain, decision writer and optional Graph credential. Constructors do not connect or start timers. A durable deployment uses ten pools with reads only, eleven with reads and decisions, or fourteen with Graph, reads and decisions.

Mandatory WORKER_AUTHORIZATION readiness includes actual read-store posture and the read-provider probe, alongside processing/canary and optional decision checks. Source options cannot replace the bound reader, drain, readiness or HTTP component. Read audit phases are ATTEMPT and PREPARED; PREPARED records a bounded item count before final authority checks and does not assert client delivery. No cursor, result content or item payload is sent to the audit callback. Failed audit acknowledgement prevents metadata release.

Managed reads retain local capacity, global INGRESS leases, actual provider callbacks and late connection acknowledgements through cancellation. The store waits for actual authorization/audit callback completion even when its transaction deadline disconnects PostgreSQL. Leases are acquired without discarding their acknowledgements on local cancellation, and are released before successful response completion. Missing acquisition/release acknowledgements latch uncertainty and prevent optimistic readiness/restart. Probes retain all sibling/provider ownership through failure/cancellation, and stop joins active reads and probes. Read callbacks must be side-effect free except the explicit deployment audit sink.

Shared drain health also fixes a concurrent snapshot race exposed by the existing Graph integration case. A database count is compared only with local leases held continuously throughout that remote read; newly acknowledged or released leases cannot invalidate an earlier valid snapshot. Continuously held lease undercounts, stale generations and unresolved acknowledgements still fail closed. Health briefly retries owned acquisition/release acknowledgement transitions without treating elapsed time as proof of completion; lost replies and control uncertainty remain unready.
